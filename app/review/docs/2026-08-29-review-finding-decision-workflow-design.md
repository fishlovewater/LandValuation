# Review 疑點決策工作流程改善設計

## 1. 目標

讓審查人員先看到可直接判斷的案件資訊，需要處理某筆疑點時才展開證據、法規與決策表單；儲存後保留工作位置並清楚顯示決策狀態。產品畫面不再直接暴露 UUID、SHA-256、頁面座標等系統追溯資料。

## 2. 已確認的事實與範圍

- 原始查估流程只有審查、退回補正及重新送審，沒有已定義的專家轉派流程。
- 目前 `EXPERT_REVIEW` 只會記錄狀態，沒有專家名單、轉派對象、專家工作清單、通知或交接流程。
- Review 只讀取既有原文件與抽取欄位，不執行 OCR、Textract 或其他文件辨識。
- 原始 PDF 與抽取文字分開保存，透過文件、版本與頁碼建立追溯關聯。
- 本次只修改 `app/review/**`，不新增 migration、前端框架、OCR 或通知功能。

## 3. 疑點清單與展開方式

每筆疑點預設顯示摘要卡片，不直接展開全部證據與表單。摘要保留：

- 中文風險等級。
- 疑點標題與簡短說明。
- 申報值與系統值。
- 原文件名稱、版本與頁碼。
- 決策狀態。

尚未決策的疑點顯示「待決策」及「開始審核」。已產生決策的疑點顯示「已決策：採納疑點／部分採納／不採納／要求補件」及「查看決策」。點擊後才展開：

- 原始文字與可讀證據。
- 法規依據。
- 原文件預覽。
- 決策理由與操作表單，或既有決策內容。

同一時間允許使用者自行展開多筆疑點；頁面重新載入後至少保留目前操作的疑點與「疑點與決策」頁籤。

## 4. 儲存後狀態與錯誤提示

儲存疑點決策成功後：

1. 重新取得案件資料。
2. 保持「疑點與決策」頁籤，不跳回「摘要與文件」。
3. 保持該筆疑點展開。
4. 顯示中文決策狀態及成功訊息。
5. 更新未處理疑點摘要數量。

決策理由為所有疑點決策的必填欄位；部分採納另需填寫「採納後的正式值」。缺少內容時不送 API，並在對應欄位下方顯示紅色中文訊息、自動聚焦第一個錯誤欄位，同時保留頁面上方的整體錯誤訊息。錯誤提示需使用 `aria-live` 或等效語意，讓輔助工具可讀取。

## 5. 法規依據與系統追溯資料

法規依據主畫面只顯示可供審查判斷的中文欄位：

- 規則名稱。
- 規則代碼。
- 規則版本名稱與版次。
- 生效日期。
- 有效截止日；空值顯示「持續有效」。
- 法規文件版本。

後端建立 finding 的 `legal_basis` 時，從既有 `validation_rules` 與 `rule_versions` 加入 `rule_name`、`version_name`、`version_no`，不得由前端猜測名稱。既有 `rule_version_id` 仍保存在資料庫與 API 追溯資料中，但審查主畫面不顯示。

以下欄位不出現在審查主畫面：

- `bounding_box`。
- `checksum_sha256`。
- `rule_version_id`。
- `source_id`。
- `document_id`。
- `validation_rule_id`。
- `extracted_field_id`。
- `extraction_run_id`。
- `knowledge_document_id`。

若未來需要查核技術資料，只能放在預設關閉的開發資訊區，不混入審查內容。

## 6. 專家覆核選項

從新的疑點決策與案件決策選單移除「轉專家覆核」。後端既有列舉值、資料表與歷史資料暫不刪除，避免 migration 與既有資料相容性風險。

若案件或疑點已存在 `EXPERT_REVIEW` 歷史狀態，畫面只顯示「專業覆核（既有資料）」狀態，不提供新的轉派操作，也不得宣稱已轉給任何人。未來只有在定義專家角色、選擇對象、工作清單、通知及交接紀錄後，才重新開放轉派功能。

## 7. 資料流

1. 工作台詳細 API 回傳 finding 的既有 `status`、決策歷程及可讀法規欄位。
2. 前端以 finding `status` 和最新 finding decision 決定狀態標籤與唯讀內容。
3. 使用者展開疑點後才請求原文件 PDF，避免清單載入時下載所有文件。
4. 儲存決策後重新載入案件，但由前端保存 active tab 與 expanded finding IDs。
5. 系統追溯欄位仍留在資料層，不進入主畫面。

## 8. 測試與驗收

- 行為測試：儲存後仍停留「疑點與決策」，並保持該筆疑點展開。
- 行為測試：未填理由或部分採納未填正式值時不送 API，顯示行內提示並聚焦欄位。
- 行為測試：已決策疑點顯示中文狀態。
- 靜態 UI 測試：兩個決策選單都沒有新的 `EXPERT_REVIEW` 選項。
- 法規測試：主畫面顯示規則名稱、版本名稱、版次與中文有效期間。
- 隱藏測試：UUID、SHA-256、座標與來源 ID 不出現在審查主畫面。
- 相容測試：既有 `EXPERT_REVIEW` 資料可唯讀顯示。
- 回歸測試：完整 Review pytest 與 Node UI 行為測試通過。
- 瀏覽器驗收：實際操作摘要、展開、缺值提示、儲存、頁籤保留與 PDF 延遲載入。

## 9. 不在本次範圍

- 實作 OCR、Textract 或 PDF 文字框選。
- 在右側原始文字加上替代性的螢光標記；本次不做可能被誤認為 PDF 精確定位的替代效果。
- 建立專家角色、專家名單、工作清單、通知或協作留言。
- 刪除後端 `EXPERT_REVIEW` 列舉值或進行資料 migration。
- 改動 `app/review/**` 以外的檔案。

## 10. 未來代辦：PDF 精確螢光標示

未來以完整 PDF 精確標示方案獨立設計與實作，不納入本次疑點決策改善。指定方向如下：

- 導入 PDF.js 或同等的自製 PDF 預覽器，取代瀏覽器內建 PDF iframe。
- 使用抽取資料提供的真實 `page_number` 與 `bounding_box`，換算 PDF 頁面座標並繪製黃色半透明標記。
- 點選疑點時，自動切換到對應頁面、捲動到標記位置並保持適合閱讀的縮放比例。
- 同頁存在多個來源區塊時，可顯示多個標記，但目前選取的疑點需有較明顯的主標記。
- 座標缺失、超出頁面或文件版本不一致時，不得猜測位置；需明確顯示「此資料尚無可用定位座標」。
- PDF.js 與座標轉換需另行評估套件來源、安全更新、效能、行動裝置閱讀及無障礙操作。
- 功能驗收必須使用具有真實 `bounding_box` 的文件，不得以 Demo 假座標宣稱定位完成。
