# 智慧審查 Run 結果與人工處理狀態設計

## 背景

目前「版本與歷次審查」將每次 Run 顯示為「通過／警示／失敗」。這三個數字實際描述規則執行當下的機器比對結果，但「失敗」容易被誤解為案件或人工審查失敗。即使審查人員確認原申報值合理，歷史 Run 仍會顯示失敗數，造成決策已完成但畫面看似仍未通過的矛盾。

## 目標

- 保留每次 Run 的不可變機器比對紀錄。
- 用詞只描述規則比對，不暗示案件核定結果。
- 將人工處理進度與機器比對結果分開呈現。
- 不修改後端統計、資料庫欄位、規則判定或案件核定流程。

## 方案比較

### 方案 A：只更換「失敗」名稱

將「失敗」改為「發現差異」。變更最小，但使用者仍需逐筆查看疑點，才知道人工處理是否完成。

### 方案 B：重新命名並增加人工處理摘要（採用）

Run 統計顯示為「符合／待專業判斷／發現差異」，另外顯示目前疑點的「已處理／待處理」數量。機器結果與人工結論各自回答不同問題，且不改寫歷史資料。

### 方案 C：人工確認後回寫 Run 為通過

畫面直觀，但會讓歷史 Run 不再忠實表示規則執行當下的結果，並混淆機器判定與人工裁量，因此不採用。

## 畫面設計

「版本與歷次審查」中的每筆 Run 使用以下標籤：

```text
第 1 次智慧審查
COMPLETED · 符合 0／待專業判斷 1／發現差異 1
```

最新案件疑點另顯示：

```text
人工處理：已處理 2／待處理 0
```

人工處理統計的定義：

- 已處理：Finding 狀態為 `ACCEPTED`、`REJECTED` 或 `PARTIALLY_ACCEPTED`。
- 待處理：Finding 狀態為 `OPEN`、`REQUIRES_SUPPLEMENT` 或 `EXPERT_REVIEW`。
- 摘要描述目前工作台載入的疑點集合，不回填至歷史 Run。

個別疑點既有狀態文字維持不變，例如「已決策：維持原申報內容」，讓使用者可追查最後採用內容。

## 資料與流程

後端繼續傳回既有 `passed_count`、`warning_count`、`failed_count`。前端只替換顯示標籤，並由已載入的 Findings 狀態計算人工處理摘要。不新增 API、不變更 schema，也不修改 Run、Finding 或 Decision。

## 錯誤與邊界

- 沒有 Run 時，維持「尚無歷次 Run」。
- 沒有 Finding 時，人工處理摘要顯示「已處理 0／待處理 0」。
- 未知 Finding 狀態不計入已處理，視為待處理，避免錯誤顯示全部完成。
- `COMPLETED` 仍表示規則執行完成，不改譯為案件通過。

## 驗收與測試

- HTML 不再用「通過／警示／失敗」描述 Run 統計。
- HTML 顯示「符合／待專業判斷／發現差異」。
- 人工處理摘要能區分最終決策狀態與待處理狀態。
- 既有疑點決策文字、API、資料模型及審查核定閘門不變。
- `app/review/tests/test_test_ui.py` 與 Review 前端靜態測試通過。

## 範圍

只修改 `app/review/test_ui/**`、對應 `app/review/tests/**` 與本設計文件。不修改其他子系統，也不改寫既有 Run 資料。
