# 第一子系統測試前端與退回補正循環設計

日期：2026-09-05

目標分支：`feature/integrate-valuation-review`

## 1. 目標

建立一個只在開發環境開放的簡易測試前端，讓估價人員不用操作 Swagger 或手動複製各種 ID，就能完成：

```text
登入
→ 建立案件與上傳文件
→ 確認 OCR／AI 候選值
→ 套入表單、計算、檢核與產生報告
→ 第一次送審
→ 查看 Review 退回原因
→ 修改內容或補文件
→ 產生新版報告並重新送審
→ Review 收到新版並重檢
```

這是測試與 Demo 工具，不是正式產品前端。

## 2. 設計原則

- 使用現有 FastAPI 提供單一 HTML 頁面，不新增 Vue、React、Node 建置流程或前端伺服器。
- 優先呼叫現有 Valuation、Submission 與 Review 服務，不另建第二套估價或補正流程。
- Valuation 是案件、擷取值、表單、計算及正式報告的權威來源。
- Review 建立修正要求，但不直接修改 Valuation 的正式內容。
- 只有人工確認且狀態為 `APPLIED` 的值可進入正式計算與送審資料。
- 每次送審建立新版本；舊 Submission、報告、Run、finding 與決策不得被覆寫。
- 前端使用中文業務語意，原始 enum、UUID 與 request ID 收在可展開的開發資訊區。
- 頁面及 Demo 帳號工具只可在 `APP_ENV=development` 使用。

## 3. 使用者流程

### 3.1 第一次製作與送審

1. 估價人員使用測試帳號登入。
2. 填寫案件基本資料、至少一筆宗地與比準地。
3. 一次選取多個 PDF、圖片或 Excel；系統先自動判斷文件類型，無法確定時由使用者選擇。
4. 呼叫既有 `POST /api/v1/valuation/auto-workflows/intake` 建立案件、保存原始文件並執行可用的擷取流程。
5. 以卡片顯示中文欄位名稱、擷取值、正規化值、來源檔案、頁碼與信心程度。
6. 使用者逐筆選擇「確認採用」或「不採用」，再呼叫既有 confirm API。
7. 前端顯示已套入欄位、缺少欄位、警告及下一步，不把候選值誤稱為正式值。
8. 完成必要表單、Decimal 計算、檢核及正式報告後才開放「送交審查」。
9. 送審成功後顯示「審查中」、送審版次與時間；案件內容轉為唯讀。

### 3.2 Review 退回補正

1. Review 送出修正通知時，Review 狀態為 `RETURNED_FOR_REVISION`，同一案件的 Valuation 狀態為 `REVISION_REQUIRED`。
2. Valuation 測試前端將案件顯示為「退回補正」，並顯示通知內容、期限及逐項修正要求。
3. 修正項目分成兩種中文類別：
   - **內容需要修改**：欄位、計算、表單或報告內容有問題。
   - **需要補充資料**：缺少文件或證明資料。
4. 估價人員在同一頁修改表單或上傳新版文件，重新執行擷取、人工確認、計算及檢核。
5. 新版報告通過送審條件後，使用者按「重新送審」。
6. 系統建立下一版 Submission，沿用同一個 Review，並自動把新版正式報告登記為修正回覆。
7. Review 的修正通知自動轉為「已收到修正版」，不要求任何人手動複製文件 ID 或版本號。
8. Review 人員仍在 Review 工作台按下「執行新版重檢」；重檢結果建立新 Run，不覆寫舊 Run。

### 3.3 案件狀態顯示

| 系統狀態 | 前端中文 |
|---|---|
| `DRAFT`、`PROCESSING` | 製作中 |
| 送審條件全部完成 | 可以送審 |
| `IN_REVIEW` | 審查中 |
| `REVISION_REQUIRED` | 退回補正 |
| 新版 Submission 已建立 | 已重新送審 |
| `REVIEW_COMPLETED` | 審查完成 |

Review 與 Valuation 的退回狀態名稱不同，前端可顯示相同中文，但後端不得把兩個欄位合併。

## 4. 頁面結構

### 4.1 登入畫面

- 帳號與密碼輸入。
- 顯示建立測試帳號的可複製指令。
- Token 僅保存於 `sessionStorage`，登出或關閉分頁即清除。

### 4.2 案件清單

- 依「製作中／審查中／退回補正／已完成」分組。
- 顯示案件編號、名稱、目前狀態、送審版次及補正期限。
- 「退回補正」案件置頂，但不改變正式資料中的優先順序。

### 4.3 製作工作區

- 步驟一：案件、宗地與比準地。
- 步驟二：文件上傳與分類。
- 步驟三：OCR／AI 候選確認。
- 步驟四：表單完成度、計算、檢核及報告。
- 步驟五：第一次送審或重新送審。

尚未完成的必要條件以中文清單顯示。沒有達到條件時，送審按鈕保持停用並說明原因。

### 4.4 補正工作區

- 顯示 Review 通知、補正期限及修正項目。
- 每項顯示問題摘要、要求修正內容、來源文件與頁碼。
- 提供「修改內容」或「補上新版文件」入口。
- 已完成的本地修改可標示進度，但 Review 的修正項目狀態只能由正式重送與重檢更新。

### 4.5 開發資訊

- 收合顯示 case ID、submission ID、review ID、文件 ID、request ID 與去敏後請求紀錄。
- 不顯示密碼、JWT、MinIO bucket、object key 或長效下載網址。

## 5. 後端銜接

### 5.1 測試頁路由

新增 `GET /api/v1/valuation/test-ui`，只在 development 回傳 HTML；其他環境回傳 404。

### 5.2 查估端可讀的送審狀態

新增 Valuation 權限下的案件送審狀態查詢，回傳：

- Valuation 案件狀態。
- 最新 Submission 的版次與時間。
- Review 的對外狀態。
- 有效修正通知的訊息、期限與可公開給估價人員的修正項目。

查詢必須驗證案件建立者或被授權的估價人員，不直接開放既有 reviewer-only API，也不回傳 Review 的內部筆記或完整 Snapshot。

### 5.3 自動銜接重新送審

沿用既有 `submit-for-review` 命令。案件為 `REVISION_REQUIRED` 時，後端在同一交易內：

1. 驗證案件版本晚於前次送審版本。
2. 驗證新版報告、檢核 Run、APPLIED 欄位與正式計算都屬於同一案件。
3. 建立下一版不可變 Submission。
4. 沿用原 Review 並更新 `latest_submission_id`。
5. 以伺服器查得的正式報告文件 ID 與版本登記修正回覆。
6. 將修正通知設為 `RESUBMITTED`，案件回到 `IN_REVIEW`。

若任何一步失敗，整筆交易回滾，不留下「已送審但 Review 沒收到新版」的半完成狀態。既有 Review 手動登記新版 API 保留給舊資料或管理用途，測試前端不再要求使用者操作。

### 5.4 測試帳號

提供 development-only 的 Valuation Demo 指令，建立具有案件、文件、估價更新、下載及送審權限的 APPRAISER 測試帳號。密碼由指令輸出，不寫死在 HTML。

## 6. 錯誤與恢復

- 登入失敗：停留在登入頁，不保留密碼。
- 擷取或 AI 未設定：保留已上傳文件，清楚標示可人工繼續的步驟。
- 必填資料不足：顯示缺少項目，不允許送審。
- 案件版本過期：重新載入案件及送審狀態，要求使用者確認後再操作。
- 重複按送審：沿用 request ID 的冪等行為，不建立重複 Submission。
- 補正期限已過：顯示逾期但仍允許依後端規則完成補正，不由前端自行阻擋。
- 網路中斷：不假設操作成功，重新查詢伺服器狀態後恢復畫面。

## 7. 測試策略

### 7.1 自動測試

- 測試頁只在 development 開放。
- APPRAISER 只能查看自己有權限的案件與修正通知。
- 回應不包含 Snapshot、內部 Review 筆記、bucket 或 object key。
- 第一次送審建立 Submission 1。
- 退回後，資料修正並重送會建立 Submission 2，並自動把修正通知轉為 `RESUBMITTED`。
- 補文件重送也會建立新文件版本與 Submission 2。
- 過期案件版本、錯誤文件、其他案件文件及重複重送會安全失敗。
- 重送失敗時 Submission 與修正通知一起回滾。
- 舊 Submission、Run、finding、決策及文件雜湊保持不變。
- JavaScript 測試涵蓋中文狀態、候選確認、送審門檻、退回顯示、去敏與重新載入。

### 7.2 真實整合與瀏覽器驗收

使用隔離的 PostgreSQL 與 MinIO 跑完整情境：

```text
第一次送審
→ Review 建立並送出修正通知
→ Valuation 顯示退回原因
→ 修改內容或補上新版文件
→ 重新計算、檢核並產生新版報告
→ 重新送審
→ Review 自動看到修正版
→ Review 執行新版重檢
```

最後必須使用真實瀏覽器完成一次，不以靜態 HTML 或 Node 測試代替瀏覽器驗收。

## 8. 不包含項目

- 不建立正式 Vue／React 產品前端。
- 不新增通知中心、Email、簡訊或背景工作。
- 不讓 Review 修改 Valuation 正式值。
- 不自動替估價人員確認 AI 候選值。
- 不自動替 Review 執行重檢或作出通過決定。
- 不重做既有 Review 工作台、修正通知或報告功能。
- 不修改、刪除或合併 `feature/review` 與 `origin/feature/valuation`。

## 9. 驗收標準

- 非技術使用者可從一個頁面完成首次製作與送審。
- 退回案件能直接看到原因、修改要求、缺件與期限。
- 能在同一頁完成修改或補件並重新送審。
- Review 自動收到正確新版，不需要人工傳遞 ID。
- 任何未完成的候選確認、計算、檢核或正式報告都會阻止送審。
- 第一次與第二次送審的歷史、文件與檢核結果都可追溯且不可覆寫。
- Production 無法開啟測試頁或使用 Demo 帳號工具。
